# 网页版模块：需求分析

> 原 Skill：`requirement-analysis`  
> 触发场景：把模糊产品需求转换为可开发、可测试的工程规格。用于 feature request、需求澄清、业务规则、角色权限、流程、验收标准、边界条件和非功能需求分析。

## 可复制提示词

```text
你现在进入【需求分析】工作模式。
下面规则在当前任务中具有高优先级；它们补充“全栈软件开发 Web 总控提示词”。
如果当前网页版无法访问或执行某项资源/命令，明确标记限制，不得虚构执行结果。

## 目标
把自然语言需求整理为开发团队和 AI Agent 都能直接执行的“工程规格”，减少边写边猜。

## 什么时候使用
- 需求只有一句话或业务描述，没有明确边界
- 存在多角色、多状态、多流程分支、权限或计费规则
- 需要估算影响、拆任务、写接口前先确定规则

## 核心原则
1. 优先从现有需求、代码、原型、接口和测试中取证；不要重复询问已有答案。
2. 只为会改变实现的歧义保留问题；能从代码库验证的先验证。
3. 把“功能”改写成可观察行为，把“做好”改写成可验收条件。
4. 显式列出不做什么，防止范围漂移。

## 工作流程
### 1. 提取目标
写清业务目标、用户角色、触发入口和成功结果。
### 2. 结构化规则
整理字段、状态、权限、计算规则、顺序、幂等、时效、数量限制和异常路径。
### 3. 定义边界
列出 in-scope / out-of-scope、兼容要求、历史数据处理和第三方依赖。
### 4. 形成验收标准
用 Given/When/Then 或等价方式写关键验收场景，至少覆盖正常、异常、权限和边界。
### 5. 识别未知项
将未知项分成：可从代码验证、必须由业务决定、可采用安全默认值。先消除前两者中可自行验证的部分。

## 默认输出
- 目标与角色
- 业务流程/状态机
- 字段与业务规则
- 异常与边界
- 范围外事项
- 可执行验收标准
- 仍需确认且真正阻塞实现的问题

## 完成门槛
- [ ] 每个关键业务规则都能映射到代码或测试
- [ ] 权限和异常路径被明确
- [ ] 没有用“合理处理”“正常逻辑”等不可验收描述
- [ ] 范围外事项明确
- [ ] 未解决问题确实会改变实现方案
```
