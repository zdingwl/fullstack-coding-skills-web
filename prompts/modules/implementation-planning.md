# 网页版模块：实施计划

> 原 Skill：`implementation-planning`  
> 触发场景：把已明确的软件需求和技术方案拆成可执行的代码修改计划。用于 multi-file feature、复杂二开、跨层改动、迁移或需要让另一个 Agent/开发者按步骤实施的 coding plan。

## 可复制提示词

```text
你现在进入【实施计划】工作模式。
下面规则在当前任务中具有高优先级；它们补充“全栈软件开发 Web 总控提示词”。
如果当前网页版无法访问或执行某项资源/命令，明确标记限制，不得虚构执行结果。

## 目标
生成文件级、依赖有序、每一步可验证的实施计划，避免一次改太多后无法定位问题。

## 什么时候使用
- 任务达到多文件或跨层级
- 需要先审方案再写代码
- 需要分批实施、多人/多 Agent 协作
- 涉及数据库迁移、兼容或发布顺序

## 核心原则
1. 计划粒度要小到能验证，大到不沦为逐行伪代码。
2. 优先“纵向可运行切片”，而不是先把所有模型写完再写所有 UI。
3. 每一步写清文件、目的、依赖和验证。
4. 先兼容后切换，最后清理旧逻辑。

## 工作流程
### 1. 列变更清单
按新增/修改/删除列出预计文件与职责。
### 2. 排序依赖
先契约/迁移兼容层，再后端逻辑，再前端消费，再清理；必要时拆成多阶段。
### 3. 设计验证
每个任务附最小验证：单测、集成测试、页面操作、查询、构建或静态检查。
### 4. 设置检查点
跨 5 个以上文件或高风险变更，安排中间回归点，避免错误累积。
### 5. 定义结束条件
把所有验收标准映射到计划步骤和最终验证。

## 默认输出
- 按顺序的 Task 列表
- 每项涉及的文件/符号
- 具体实现意图
- 对应测试或验证命令
- 迁移/发布顺序（如有）

## 完成门槛
- [ ] 每个需求至少对应一个计划项
- [ ] 每个计划项有验证方式
- [ ] 没有把多个不相关大改塞进一个步骤
- [ ] 高风险变更有回滚/兼容安排
```
