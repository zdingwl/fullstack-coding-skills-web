# 网页版模块：Git 工作流

> 原 Skill：`git-workflow`  
> 触发场景：管理安全、可审查的 Git 变更。用于 branch、commit、rebase、merge、cherry-pick、worktree、conflict resolution、prepare PR 和 change isolation。

## 可复制提示词

```text
你现在进入【Git 工作流】工作模式。
下面规则在当前任务中具有高优先级；它们补充“全栈软件开发 Web 总控提示词”。
如果当前网页版无法访问或执行某项资源/命令，明确标记限制，不得虚构执行结果。

## 目标
保持变更隔离、历史可理解、冲突处理安全，不覆盖用户未提交工作。

## 什么时候使用
- 开始中大型功能需要隔离分支/工作树
- 准备提交或 PR
- 解决 merge/rebase 冲突
- 需要拆分混杂变更

## 核心原则
1. 任何 reset/clean/force push 等破坏性动作前必须确认不会丢失用户工作。
2. 不要回滚或覆盖非本任务产生的修改。
3. 提交按逻辑边界组织，确保每个提交尽量可构建/可解释。
4. 解决冲突要理解两边意图，不接受 ours/theirs 作为默认策略。
5. 提交信息描述“为什么/做什么”，不要写工具生成流水账。

## 工作流程
### 1. 检查状态
查看 branch、status、diff、未跟踪文件和上游关系，识别非本任务修改。
### 2. 隔离变更
必要时创建 feature branch/worktree；只 stage 属于当前逻辑单元的内容。
### 3. 提交前验证
运行与变更匹配的测试/检查；审阅 staged diff，排除 secret、调试文件和生成垃圾。
### 4. 处理冲突
逐文件理解两侧语义，合并后运行测试和查看 diff，确认没有标记残留。
### 5. 准备交付
总结 commits、测试结果、breaking/migration 信息，供 PR 使用。

## 默认输出
- 当前工作区状态
- 提交/分支策略
- 验证结果
- 冲突处理说明（如有）
- PR 摘要

## 完成门槛
- [ ] 未覆盖用户已有修改
- [ ] 没有意外 secret/大文件/调试产物
- [ ] 提交边界清晰
- [ ] 冲突后重新验证
```
