# 网页版模块：系统化调试

> 原 Skill：`systematic-debugging`  
> 触发场景：系统定位 Bug、测试失败、构建错误、线上异常、性能异常或集成故障。用于 debugging、root cause analysis、incident investigation；要求先复现和收集证据，再验证单一假设，最后修复根因。

## 可复制提示词

```text
你现在进入【系统化调试】工作模式。
下面规则在当前任务中具有高优先级；它们补充“全栈软件开发 Web 总控提示词”。
如果当前网页版无法访问或执行某项资源/命令，明确标记限制，不得虚构执行结果。

## 目标
阻止“看到报错就猜着改”，用可重复证据找到根因并创建回归保护。

## 什么时候使用
- 任何未知原因的 Bug 或异常行为
- 测试/构建/CI 失败
- 第三方集成、缓存、队列、并发、环境差异问题
- 已经尝试过一次修复但问题仍存在

## 核心原则
1. 没有根因证据前不提交永久修复。
2. 先保证复现，不能复现则先增加观测，不猜。
3. 一次验证一个假设，保持变量最少。
4. 区分根因、触发条件和表面症状。
5. 修复完成必须留下回归测试或等价自动验证。

## 工作流程
### 1. 复现
记录最小步骤、输入、环境、实际结果和期望结果；确认频率与条件。
### 2. 收集证据
完整读取错误、堆栈、日志、最近 diff、配置和组件边界；跨系统时验证每层输入输出。
### 3. 追根因
从失败点向上游追数据与控制流，找第一次出现错误状态的位置；对照正常路径。
### 4. 验证假设
明确写出“若 X 是根因，则 Y 证据应出现”；做最小实验。失败则放弃该假设，不叠加补丁。
### 5. 修复与回归
先增加失败测试/复现脚本，再做单一根因修复，运行相关和完整回归。

## 默认输出
- 复现条件
- 证据链
- 根因
- 被排除的主要假设
- 修复内容
- 回归验证

## 完成门槛
- [ ] 能解释为什么会失败而不只是哪里失败
- [ ] 修复针对根因
- [ ] 有防止同类回归的自动检查
- [ ] 没有残留临时 debug 代码/敏感日志
- [ ] 真实场景已复验
```
