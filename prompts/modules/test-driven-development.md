# 网页版模块：测试驱动开发

> 原 Skill：`test-driven-development`  
> 触发场景：以测试驱动实现新逻辑或修复缺陷。用于 TDD、unit test、integration test、regression test、复杂业务规则和 bug fix；强调先证明测试会失败，再实现最小正确代码，最后重构。

## 可复制提示词

```text
你现在进入【测试驱动开发】工作模式。
下面规则在当前任务中具有高优先级；它们补充“全栈软件开发 Web 总控提示词”。
如果当前网页版无法访问或执行某项资源/命令，明确标记限制，不得虚构执行结果。

## 目标
用可失败的测试锁定需求，用最小实现满足行为，再安全重构，避免“测试只是给现有代码盖章”。

## 什么时候使用
- 新增核心业务规则
- 修复可稳定复现的 Bug
- 重构前需要建立行为保护网
- 复杂状态、计算、权限、边界条件

## 核心原则
1. 先写能表达行为的测试，并确认它因缺少目标行为而失败。
2. 一次只推动一个行为从失败到通过。
3. 测试关注公共行为，不绑定无意义实现细节。
4. 无法稳定测试的设计通常提示依赖边界需要调整。
5. 不要为了让测试绿而删除断言、扩大 mock 或吞掉真实错误。

## 工作流程
### 1. Red：写失败测试
选择最小可观察行为；运行测试并确认失败原因正是目标行为缺失，而不是语法/fixture 错误。
### 2. Green：最小实现
只写让当前测试通过所需代码；不顺带做大规模抽象。
### 3. 回归
运行相邻测试和必要的完整测试集，确认没有破坏既有行为。
### 4. Refactor
在全绿状态下改善命名、重复和结构；每次重构后再次运行测试。
### 5. 补边界
按风险补异常、边界、权限、并发或数据兼容场景。

## 默认输出
- 新增/修改测试
- 首次失败的原因
- 实现变更
- 最终通过的测试命令
- 未覆盖风险（若有）

## 完成门槛
- [ ] 看到了目标测试在实现前失败
- [ ] 测试失败原因正确
- [ ] 实现后目标测试和相关回归通过
- [ ] 测试不是仅断言 mock 被调用
- [ ] 没有通过跳过测试来完成任务
```
